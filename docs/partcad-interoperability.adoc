= PartCAD interoperability boundary

Status: decision spike for Issue #37.

== Decision

EMES keeps authority over semantic mechanism IR, requirements, design intent, canonical identity, source-conditioned engineering facts, evidence lineage, verification, and design acceptance.

PartCAD is reused at the artifact/package boundary where it already provides package management, CAD object handling, assemblies, ports/interfaces/mates, sourcing/provider infrastructure, BOM-oriented workflows, and manufacturing/assembly documentation.

The minimum interoperability seam is a file boundary. EMES generates ordinary interchange artifacts such as STEP or URDF. A PartCAD package may register those artifacts without making PartCAD the source of truth for EMES semantics. No PartCAD runtime dependency is required by EMES for this seam.

== Observed PartCAD version

The spike inspected PartCAD development commit `b8a6caa915f53af7eca6bd1868e340f218b81d0b`, whose Python package reports version `0.8.64`. PartCAD is Apache-2.0 licensed.

Relevant upstream sources inspected at that commit include `README.md`, `docs/source/assy.rst`, `docs/source/configuration.rst`, `docs/source/cli.rst`, `src/partcad_utils/schema/partcad.json`, and `requirements.txt`.

The observed implementation supports STEP parts, Assembly YAML, ports/interfaces/mates, package dependencies, providers, vendor/SKU metadata, multiple CAD backends, and export/render workflows. These are treated as external capabilities rather than reimplemented inside EMES.

== Practical proof

The existing `examples/two-link-arm/mechanism.json` was executed through the normal EMES reference loop to produce `generated/two-link-arm/arm.step` while preserving EMES' own deterministic BREP/MJCF/evidence checks.

A minimal external PartCAD package then registered that projection directly:

[source,yaml]
----
desc: EMES PartCAD interoperability spike; STEP remains a derived EMES projection.
parts:
  emes-two-link-arm:
    type: step
    path: two-link-arm.step
----

With the generated STEP copied to `two-link-arm.step`, PartCAD `pc list parts` recognized exactly one part, `emes-two-link-arm`. No EMES-to-PartCAD semantic converter was needed.

A subsequent shape-materialization attempt on a Python 3.14 host exposed a PartCAD sandbox dependency incompatibility around `backports.zstd`. This is an external runtime/toolchain constraint, not a reason to move canonical semantics into PartCAD. The file-level interoperability proof remains valid and intentionally avoids making PartCAD a required EMES dependency.

== Capability boundary

[cols="1,1,3",options="header"]
|===
|Concern |Disposition |Reason

|Requirements and design intent
|Keep EMES-owned
|They drive engineering verification and must remain tied to canonical EMES identity.

|Canonical semantic mechanism graph and digest
|Keep EMES-owned
|PartCAD package/object identity is useful externally but is not an equivalent semantic design identity.

|Source-conditioned manufacturer engineering facts
|Keep EMES-owned
|EMES currently fails closed on exact operating conditions and evidence provenance. Flattening these facts into generic package metadata would be lossy.

|Evidence lineage, verification state, acceptance decision
|Keep EMES-owned
|These are core trust boundaries between proposed design and engineering evidence.

|CAD generation and simulation adapters
|Interoperate
|EMES selects and records analysis intent; generated STEP/BREP/URDF/MJCF or other adapter artifacts may be handed to external tools.

|STEP/BREP/STL and other CAD object handling
|Reuse PartCAD where useful
|PartCAD already imports, converts, renders, exports, caches, and opens common CAD artifacts.

|Package/dependency management
|Reuse PartCAD rather than clone
|EMES does not need another general hardware package manager.

|Assembly representation, BOM-oriented traversal, assembly instructions
|Reuse or interoperate
|PartCAD Assembly YAML already covers nested parts/assemblies and connection-oriented assembly information.

|Ports, interfaces, mates
|Interoperate, do not equate blindly
|PartCAD's model is richer than EMES' current endpoint strings. Mapping is useful only when EMES has explicit compatible frame/interface semantics; unsupported mappings must fail closed.

|Vendor/SKU/provider/sourcing infrastructure
|Reuse where the need is commercial/supply-chain oriented
|PartCAD already represents vendor/SKU and provider concepts. EMES should retain only engineering facts and snapshot identity required for reproducible analysis.

|AI part search/generation workflows
|Reuse externally when beneficial
|PartCAD already exposes agent-oriented commands and workflows; EMES should consume resulting candidate artifacts/data through explicit trust boundaries.
|===

== Lossy or unsupported mappings

The following must not be inferred automatically:

* an EMES connection endpoint is not automatically a PartCAD port or interface;
* an EMES component is not automatically a PartCAD purchasable part;
* a PartCAD vendor/SKU record is not sufficient evidence for an EMES performance rating;
* a PartCAD validation result is not automatically an EMES evidence envelope;
* an EMES source-conditioned property must not be reduced to an unconditional PartCAD metadata field;
* EMES canonical digests must not be replaced with PartCAD package, object, or file identity.

Interop code must therefore prefer explicit mappings and reject missing semantics rather than inventing them.

== Consequence for Issue #5

Issue #5 should be reduced before implementation. EMES should not build generic package management, generic provider infrastructure, general CAD artifact catalogs, generic assembly/BOM machinery, or a competing interface/mating framework merely to reproduce PartCAD capabilities.

The remaining EMES catalog work should concentrate on what directly affects engineering reasoning and reproducibility:

* typed engineering properties, performance curves, operating envelopes, tolerances, uncertainty, and measurement provenance;
* exact source conditions and evidence provenance;
* compatibility predicates that materially affect EMES analyses and acceptance;
* immutable snapshot/digest binding between a mechanism and the engineering facts used by evaluators;
* selection/ranking inputs required by EMES optimizers, while delegating broader discovery/sourcing where an external package/provider system is sufficient;
* schema evolution only after multiple real engineering catalogs demonstrate a concrete need.

== Next implementation seam

Issue #38 should implement only the smallest seam justified by this spike: an optional export/package helper around an existing EMES-generated artifact, or equivalent file/CLI integration. It must remain optional, must not move EMES canonical authority, and must not introduce PartCAD as a hard runtime dependency unless a later concrete requirement proves that a file/CLI boundary is insufficient.
