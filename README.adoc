= EMES
:toc:

EMES (Executable Mechanical Engineering Specification) is an AI-native architecture for describing, generating, verifying, and iterating mechanical mechanisms as structured, version-controlled engineering data.

== Core idea

CAD is a derived artifact, not the source of truth.

[source,text]
----
requirements + design intent
          |
          v
 semantic mechanism IR
          |
    +-----+------+----------------+
    |            |                |
    v            v                v
  CAD         simulation       BOM / DFM
    \            |                /
     +-----------+---------------+
                 v
       deterministic evidence
                 |
                 v
        AI / optimizer patch
                 |
                 +------> repeat
----

The canonical source records requirements, topology, parameters, interfaces, load cases, objectives, constraints, and analysis intent. Generated CAD, simulation models, solver decks, reports, and BOMs remain reproducible projections.

A key architectural boundary is the separation between the semantic design graph and the evidence graph: AI may propose changes to the design, while registered tools and measurements produce the evidence used to accept or reject those changes.

Purchased components are also explicit engineering inputs. Motors, gearboxes, bearings, sensors, fasteners, battery cells, BMS units, power supplies, and converters can be normalized into versioned catalog snapshots containing dimensions, interfaces, unit-bearing properties, performance data, and attributed assets. A mechanism binds to a specific catalog/part digest rather than a live mutable vendor record.

== Current status

The architecture foundation and first external-tool vertical slice are merged:

[source,text]
----
EMES JSON
  -> semantic + catalog validation
  -> build123d -> exact BREP + STEP
  -> MJCF -> MuJoCo
  -> machine-readable evidence
----

The catalog layer supports deterministic import and pinned part binding. A synthetic motor fixture exercises the generic import contract, while `catalogs/maxon-496661.catalog.json` exercises the same architecture with an attributable real manufacturer motor snapshot. The maxon record is regenerated offline from a reviewed source snapshot and independently checked against hash-pinned manufacturer PDF/CAD assets.

The power-system layer adds composable electrical components. A catalog-backed 21700-format cell can be combined by explicit series/parallel counts into a battery pack, constrained by a BMS, passed through a DC/DC converter, and evaluated against electrical load, energy, current, voltage, and mass constraints. Fixed DC power supplies are also executable sources.

`catalogs/molicel-p45b.catalog.json` is the first authoritative manufacturer battery-cell snapshot. It is normalized from the hash-pinned Molicel INR-21700-P45B Product Data Sheet v1.4, with an independently hash-pinned official performance page for discrete short-duration performance points. Manufacturer conditions remain attached to the engineering facts they qualify rather than being flattened into unconditional limits.

`examples/power-pack-molicel-p45b/mechanism.json` binds that real cell record to synthetic BMS/converter fixtures. The power evaluator accepts the continuous-discharge rating only when the selected BMS exposes a compatible cell cut-off control and records that check in deterministic evidence. This is an executable sizing/traceability check, not a thermal model, certification, or permission to fabricate or energize a battery pack.

The same P45B example has a separate source-conditioned battery-sag analysis. `tools/battery_sag.py` reuses the power evidence instead of recomputing the load path, applies the P45B typical DC-impedance value only at its stated 50% SOC condition, and derives first-order series/parallel pack resistance and resistive voltage drop. Unsupported SOC values are rejected rather than interpolated. The adapter deliberately does not infer loaded terminal voltage without an attributable OCV-vs-SOC model.

`tools/battery_pulse.py` consumes exact manufacturer short-duration points through a structured analysis request. The current P45B catalog exposes 168 W/cell at 10 s and 50% SOC and 184 W/cell at 10 s and 90% SOC. An unsupported SOC or duration is rejected rather than interpolated or extrapolated.

`tools/battery_known_envelope.py` then combines the cell pulse envelope with currently known downstream BMS and converter limits using dimensionless load-scale factors while preserving each rating's native unit. In the reference 10S2P/500 W case the synthetic converter is the current weakest known component at a 1.44 load-scale factor, corresponding to a 720 W output envelope. This is deliberately not described as a complete system pulse rating because fuse, interconnect, conductor, connector, contactor, thermal, imbalance, aging, and enclosure limits remain unmodeled.

A custom EMES language remains intentionally deferred until concrete examples prove it is necessary.
